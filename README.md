## Приложение 'Трекер привычек'

Бэкенд-часть SPA веб-приложения для автоматизации формирования полезных привычек, 
разработанная по мотивам всемирно известного бестселлера Джеймса Клира «Атомные привычки». 
Проект позволяет пользователям проходить регистрацию, управлять своим профилем, настраивать личные 
или публичные трекеры привычек, использовать систему вознаграждений и автоматически получать 
напоминания в мессенджер Telegram.

### Технологический стек
 - Язык разработки: Python 3.12+Фреймворк: Django 6.0 / Django REST Framework (DRF)
 - База данных: PostgreSQL
 - Авторизация: JWT-токены (rest_framework_simplejwt)
 - Асинхронные задачи: Celery + Redis (в качестве брокера)
 - Периодические рассылки: Django Celery Beat
 - Документация: Swagger / ReDoc (drf-yasg)
 - Тестирование и метрики: Django Testing Framework + coverage
 - Дополнительные пакеты: django_countries (работа со странами), phonenumber_field (валидация телефонов)


### Бизнес-логика и правила валидации

В соответствии с методологией формирования привычек, в системе жестко запрограммированы следующие бизнес-ограничения *(validators.py)*:
1. Исключение дублирования наград: Нельзя одновременно выбрать для одной привычки и текстовое вознаграждение, и связанную привычку *(RewardAndRelatedHabitValidator)*.
2. Ограничение времени: Время выполнения полезного действия не должно превышать 120 секунд (2 минуты) *(DurationHabitValidator)*.
3. Чистота связанных привычек: В качестве связанной привычки может выступать только та привычка, которая имеет явный признак приятной *(RelatedHabitIsPleasantValidator)*.
4. Скромность приятных привычек: Сама по себе приятная привычка не может иметь собственного вознаграждения или другой связанной привычки *(PleasantHabitValidator)*.
5. Минимальная регулярность: Нельзя настраивать выполнение привычки реже, чем 1 раз в 7 дней (в неделю) *(PeriodicityValidator)*.


### Права доступа (Permissions) и Пагинация

1. Доступ к эндпоинтам: Все эндпоинты управления привычками требуют обязательной JWT-авторизации *(IsAuthenticated)*.
2. Владение объектами: Изменение *(update)*, частичное изменение *(partial_update)*, удаление *(delete)* и детальный просмотр *(retrieve)* личных привычек доступны исключительно их создателю *(IsOwner)*. При создании новой привычки владелец *(owner)* проставляется автоматически на основе текущей сессии пользователя.
3. Пагинация: Для всех списков привычек используется кастомный постраничный вывод LimitOffsetPagination со стандартным лимитом 5 записей на страницу и максимумом до 100 записей.


### Полный список эндпоинтов API

1. Управление пользователями и авторизация (users/)

| Метод         | URL-путь                | Описание эндпоинта                                              | Доступ                      |
|:--------------|:------------------------|:----------------------------------------------------------------|:----------------------------|
| **POST**      | `/users/register/`      | Регистрация нового пользователя                                 | Доступно всем (`AllowAny`)  |
| **POST**      | `/users/login/`         | Получение JWT-токенов                                           | Доступно всем (`AllowAny`)  |
| **POST**      | `/users/token/refresh/` | Обновление истекшего access токена                              | Доступно всем (AllowAny)    |
| **GET**       | `/users/users/`         | Просмотр списка всех пользователей (сокращенный JSON)           | Авторизованные пользователи |
| **GET**       | `/users/users/<id>/`    | Детальный просмотр профиля (свой — полный, чужой — сокращенный) | Авторизованные пользователи |
| **PUT/PATCH** | `/users/users/<id>/`    | Полное или частичное редактирование своего профиля              | Только владелец (IsProfile) |
| **DELETE**    | `/users/users/<id>/`    | Удаление профиля пользователя                                   | Только владелец (IsProfile) |

1. Управление привычками (habits/)

| Метод         | URL-путь               | Описание эндпоинта                                      | Доступ                          |
|:--------------|:-----------------------|:--------------------------------------------------------|:--------------------------------|
| **GET**       | `/habits/`             | Список личных привычек текущего пользователя            | Авторизованный пользователь     |
| **GET**       | `/habits/public/`      | Список всех публичных привычек системы (is_public=True) | Все авторизованные пользователи |
| **POST**      | `/habits/create/`      | Создание новой привычки с валидацией бизнес-правил      | Авторизованный пользователь     |
| **GET**       | `/habits/<id>/`        | Детальный просмотр конкретной привычки                  | Только владелец (IsOwner)       |
| **PUT/PATCH** | `/habits/<id>/update/` | Полное или частичное редактирование привычки            | Только владелец (IsOwner)       |
| **DELETE**    | `/habits/<id>/delete/` | Безвозвратное удаление привычки из системы              | Только владелец (IsOwner)       |

Публичный формат: При вызове _/habits/public/_ сериализатор _HabitPublicSerializer_ динамически генерирует мотивирующее поле _full_sentence_ по шаблону: Я буду [Действие] в [Время] [Место].


### Логика периодических уведомлений (Celery + Telegram)
В проекте реализован автоматический фоновый механизм проверки расписания привычек с интеграцией Telegram API.
Как это работает:
1. Каждую минуту планировщик django_celery_beat вызывает асинхронную задачу send_habit_reminders *(tasks.py)*.
2. Задача определяет текущее местное время, отсекая секунды и микросекунды для точного совпадения.
3. Производится фильтрация в БД по следующим критериям:
   - Привычка является полезной *(is_pleasant=False)*.
   - День, час и минута запланированного действия совпадают с текущим временем.
   - У владельца привычки в профиле заполнен идентификатор Telegram-чата *(tg_chat_id)*.
4. Для каждой найденной привычки бот отправляет текстовое сообщение на основе шаблона:
   - "Напоминание! Вы обещали [Действие] в [Время] [Место].
5. "Автоматический сдвиг расписания: После успешной отправки уведомления дата следующего выполнения привычки *(date_time)* автоматически сдвигается вперед на количество дней, указанное в её периодичности *(periodicity)*, и объект сохраняется обратно в БД, предотвращая повторные отправки.


### Настройка и локальный запуск
1. Клонируйте репозиторий проекта
```
git clone https://github.com
cd habit-tracker
```
2. Настройте и активируйте виртуальное окружение
```
python -m venv venv
source venv/bin/activate  # Для Linux/macOS
venv\Scripts\activate     # Для Windows
```
_Проект содержит настроенный файл .gitignore, который предотвращает попадание виртуального окружения, кэша, логов и конфиденциальных данных в публичный репозиторий._
3. Установка пакетов
```
pip install -r requirements.txt
```
4. Переменные окружения
В корне проекта находится демонстрационный файл ```.env.example``` со структурой необходимых ключей. Скопируйте его и создайте личный файл ```.env```:
```
cp .env.example .env
```
Заполните ```.env``` актуальными данными подключения к PostgreSQL, Redis и токеном Telegram-бота.
5. Подготовка базы данных, фикстур и суперпользователя
```
# Выполните миграции
python manage.py migrate

# Загрузите демонстрационные данные из фикстур (пользователи и привычки)
python manage.py loaddata fixtures/users_fixture.json
python manage.py loaddata fixtures/habits_fixture.json

# Быстро создайте суперпользователя (администратора) через кастомную консольную команду csu
python manage.py csu
```
6. Одновременный запуск необходимых сервисов
Для обеспечения полноценной работы API, фоновых воркеров и периодического планировщика напоминаний, запустите три независимых процесса в разных терминалах:
- Терминал 1 (Веб-сервер Django):
```
python manage.py runserver
```
- Терминал 2 (Очередь задач Celery Worker):
```
celery -A config worker --loglevel=info
celery -A config worker -l INFO -P threads   # Для Windows
```
- Терминал 3 (Хронометр Celery Beat):
```
celery -A config beat --loglevel=info
```

### Docker и Deploy

#### Docker

Проект контейнеризирован с использованием Docker.

Используется:

- Dockerfile для сборки образа приложения
- Docker Compose для запуска всех сервисов
- Docker Hub для хранения Docker image
- GitHub Actions для автоматической сборки и деплоя

#### Dockerfile

Dockerfile находится в корне проекта.

Он выполняет:

1. Создание контейнера на основе Python 3.14
2. Установку системных зависимостей
3. Установку зависимостей Python через Poetry
4. Копирование проекта внутрь контейнера
5. Подготовку окружения для запуска Django


Сборка образа вручную:

```
docker build -t project_name .
```

#### Docker Compose

Файл: docker-compose.yml
Используется для запуска полного окружения проекта.

Сервисы:

| Сервис          | Назначение                  |
|:----------------|:----------------------------|
| **web**         | Django + Gunicorn           |   
| **db**          | PostgresSQL                 |   
| **redis**       | Redis брокер для Celery     |
| **celery**      | Выполнение фоновых задач    |
| **celery-beat** | Планировщик задач           |
| **nginx**       | Reverse pro                 |
|                 |

#### Celery

Celery использует Redis как брокер сообщений.

Worker запускается командой:
```
celery -A config worker -l INFO
```
Beat запускается:
```
celery -A config beat -l INFO
```
Проверка логов:
```
docker compose logs -f celery
docker compose logs -f celery-beat
```

#### Nginx

Nginx используется как reverse proxy.

Схема работы:
```
Пользователь
      |
      v
   Nginx :80
      |
      v
 Gunicorn :8000
      |
      v
 Django
```
Конфигурация находится:
```
nginx/nginx.conf
```
Основная задача Nginx:

 - принимать внешние HTTP-запросы;
 - передавать их Django;
 - отдавать статические файлы.

Проверка конфигурации:
```
docker compose exec nginx nginx -t
```

#### Gunicorn

Django запускается через Gunicorn:
```
gunicorn config.wsgi:application --bind 0.0.0.0:8000
```
Gunicorn работает внутри контейнера web.
